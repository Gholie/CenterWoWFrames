# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A World of Warcraft addon that re-anchors native Blizzard UI frames to a user-chosen aspect ratio (e.g. 16:9, 21:9), centered on screen. Targets two clients, shipped as one release zip:

- **Retail** — Patch 12.1 / Midnight (`120100`), i.e. the post-"addon disarmament" API era. Loads `CenterWoWFrames.toc`.
- **WoW Forever** — Patch 1.60.x (`16001`), the "Classic+" client launched Nov 2026. Loads `CenterWoWFrames_Forever.toc`, which it prefers over the unsuffixed TOC; retail ignores that suffix. Internally its game type is **`camelot`** (`WOW_PROJECT_CAMELOT = 18`). `_Camelot` is also accepted, but **`_Forever` is the suffix this project uses**. Installed under `<WoW>/_forever_/Interface/AddOns/`. It is a game type *inside the Mainline family* (`[Family]` = `Mainline`), so it runs the same Edit Mode, panel manager, managed-frame containers, action bars and unit frames as retail, with `Camelot/` override files on top. Secret Values (`issecretvalue`) exist there too. Blizzard's UI source for it is the `forever` branch of `Gethe/wow-ui-source`.

> **Keep this in sync:** whenever you bump `## Interface:` in either `.toc`, update the versions referenced above in the same change. The `.toc` files are the source of truth; this doc must not drift from them. Packaging relies on BigWigsMods/packager ≥ v2.6.0 recognising `16xxx` as Forever — don't downgrade the pin in `.github/workflows/package.yml`.

### TOCs and deployment (read before touching either `.toc`)

- `CenterWoWFrames.toc` — `## Interface: 120100, 16001`
- `CenterWoWFrames_Forever.toc` — `## Interface: 16001`

The main TOC deliberately **also lists `16001`**, even though Forever never loads it. BigWigsMods/packager (v2.6.1 and master as of Nov 2026) reads game versions only from the unsuffixed TOC and the suffixes it knows. For Forever that's `_Camelot`, not `_Forever`. It then uploads **one zip** to CurseForge tagged with every detected game version (retail via game type 517, Forever via 88568). Drop `16001` from the main TOC and releases silently stop reaching Forever users. `tests/run.lua` fails if any flavor TOC's interface is missing from the main TOC, or if the `Title`/`Version`/`SavedVariables`/`X-Curse-Project-ID` directives drift between TOCs. The `_Forever.toc` still gets `@project-version@` substituted, because packager runs keyword replacement on every `.toc`. When bumping Forever's interface, change it in **both** TOCs. If packager ever learns the `_Forever` suffix, the duplicate can go.

### When retail and Forever diverge

Both TOCs currently list the same files. Because one zip serves both clients, handle differences in this order of preference:
1. **Feature detection at runtime.** Check that the global, function, method or event exists before using it. This is the existing pattern: `RegisterOptionalEvent`, the `type(_G[name]) == "function"` guards before `hooksecurefunc`, and FRAME_LIST skipping missing frames.
2. **Explicit flavor check**, when behavior must differ even though both APIs exist: `local IS_FOREVER = WOW_PROJECT_CAMELOT ~= nil and WOW_PROJECT_ID == WOW_PROJECT_CAMELOT`. `WOW_PROJECT_CAMELOT` is nil on retail, so this is safely false there.
3. **Flavor-only files** for larger chunks, e.g. `Compat_Forever.lua`, listed only in `CenterWoWFrames_Forever.toc` after the shared files. The test harness loads each TOC's own file list, so add a scenario for the flavor-specific behavior.
4. **Don't** use packager `@version-retail@`/`@version-forever@` keyword blocks. They strip code from the single shared zip, which removes it for both clients. If the clients ever need genuinely separate builds, switch the Forever TOC to the packager-recognised `_Camelot` suffix and run a second packager job with `-g forever`, or ask packager upstream to accept `_Forever`.

There is no build or lint tooling; this is a pure Lua addon and real iteration is in-game. There *is* an offline smoke-test harness: `lua5.1 tests/run.lua` (from the repo root) loads every file listed in the `.toc` into a sandbox backed by `tests/mock_wow.lua` (a minimal horizontal-geometry mock of the WoW API: frames/anchors, combat lockdown, a simplified panel manager, the right-managed container and bag anchoring) and checks the anchor/panel math, combat deferral, slash commands, TOC well-formedness and the deploy-to-both-clients invariant, that each flavor TOC loads, and that the addon still loads on a client missing Edit Mode / panel-manager globals. CI runs it (`.github/workflows/test.yml`). Add a scenario there when you change behavior; it's excluded from releases via `.pkgmeta`. To test changes, the directory must live at `<WoW>/_retail_/Interface/AddOns/CenterWoWFrames/` or `<WoW>/_forever_/Interface/AddOns/CenterWoWFrames/` (symlink the repo there) and reload with `/reload` or `/console reloadui`. In-game slash command is `/cwf` (see `Config.lua` for subcommands: `ratio`, `toggle`, `debug`, `reload`, `status`).

## Architecture

**The CenterFrame indirection.** The core trick is in `Core.lua`: a single invisible `CWF_CenterFrame` is created as a child of `UIParent`, sized to `(UIParent.height * targetRatio) × UIParent.height`, and pinned to `UIParent`'s CENTER. Every managed Blizzard frame has its anchor list rewritten so any reference to `UIParent` is replaced with `CenterFrame`. UIParent itself is **never** modified — this is a hard invariant. When the user changes ratio, only `CenterFrame`'s size changes; WoW's layout engine re-flows everything anchored to it for free.

**Capture-then-apply, not a fixed mapping.** `Capture(frame)` reads each frame's *current* `GetPoint(i)` values (whatever Blizzard or Edit Mode set) and replays them via `SetPoint`, substituting `UIParent → CenterFrame` *only* for anchors whose relativePoint contains `LEFT` or `RIGHT` (i.e. has a horizontal-edge component). `CENTER`, `TOP`, and `BOTTOM` anchors sit on UIParent's vertical axis — which CenterFrame already shares — so rewriting them would be a visual no-op and is skipped. This means the addon respects user Edit Mode customizations and leaves screen-horizontally-centered frames where they natively are.

**Two re-anchor paths, different purposes:**
- `CaptureAndApplyAll()` — re-reads anchors from Blizzard. Called on PLAYER_ENTERING_WORLD, EDIT_MODE_LAYOUTS_UPDATED, UI_SCALE_CHANGED, DISPLAY_SIZE_CHANGED. Always deferred one frame via `C_Timer.After(0, ...)` so Blizzard finishes its own anchoring first. If it bails out on `InCombatLockdown()`, it sets a module-local `captureDropped` flag so the request isn't silently lost.
- `ReapplyStored()` — replays anchors from `storedAnchors`, but *only* for the frames recorded in the module-local `failedApplies` set (frames whose most recent `Apply` failed, typically protected frames skipped mid-combat). Frames that already applied cleanly are left alone, so legitimate mid-combat Blizzard repositioning (vehicle bar swaps, stance bar reflow, objective tracker collapse, ...) isn't reverted every time combat ends. Does not re-read from Blizzard.

On `PLAYER_REGEN_ENABLED`, Core.lua first applies any ratio/toggle change Config.lua deferred during combat (`CWF._pendingGeometryUpdate`), then calls `CaptureAndApplyAll()` if `captureDropped` is set or `storedAnchors` is still empty, otherwise `ReapplyStored()` — only after that does it call `AdjustOpenPanels()`.

**Containers Blizzard re-pins from code (`ManagedContainers.lua`).** Two more things are positioned by Blizzard code on every layout pass, so a FRAME_LIST capture can't hold them:
- `RightManagedFrameContainer` holds every `RightManagedFrameTemplate` frame — BossTargetFrameContainer (Boss1-5TargetFrame are its children), CompactArenaFrame, DurabilityFrame, VehicleSeatIndicator, QuestTimerFrame, the below-minimap widgets, and the objective tracker when not user-placed. The secure delegate's `ManageRightFrameContainer()` re-pins it to UIParent TOPRIGHT on every `ManageFramePositions()`. That is why those FRAME_LIST entries only matter once the user moves them in Edit Mode, which reparents them to UIParent.
- Right action bars in their default position: `EditModeManagerFrame:UpdateRightActionBarPositions()` re-pins `MultiBarRight`/`MultiBarLeft` to UIParent RIGHT (on display/scale changes, action-bar visibility changes, ...) and then calls `ManageFramePositions()`. They're re-anchored in the same hook so the bars and the container (offset by the bars' width) stay together.
- Bags: `UpdateContainerFrameAnchors()` pins the first shown bag to the BOTTOMRIGHT of its parent (`ContainerFrameContainer`, which is setAllPoints on UIParent, or UIParent for combined bags); the rest chain off it.

The bag list is read via `rawget(ContainerFrameSettingsManager, "bagsShown")`, **never** by calling `GetBagsShown()`. That method fills its cache lazily, and if addon code fills it, the cached table taints every later secure reader. Known limitation: Blizzard's bag auto-scale (`GetContainerScale`) measures free space against the full screen and `BankFrame:GetRight()`, so with the bank open and many bags it can under-scale and let bag columns overlap the bank.

Both globals are post-hooked with `hooksecurefunc` (installed lazily, retried on ADDON_LOADED), and the screen-sized `relativeTo` on a LEFT/RIGHT anchor is swapped for CenterFrame, keeping the offsets. The right container is implicitly protected (secure Boss unit buttons inside) and gets re-pinned mid-combat at encounter start. In that case the move is skipped (`IsProtected()` + `InCombatLockdown()`, which raises ADDON_ACTION_BLOCKED rather than a catchable error) and retried on PLAYER_REGEN_ENABLED, so boss frames sit at the screen edge for the rest of that pull. `CaptureAndApplyAll()` and PLAYER_REGEN_ENABLED both call `CWF.AdjustManagedContainers()`.

**Combat safety.** Both re-anchor paths early-return on `InCombatLockdown()`. The per-frame `Apply` call is wrapped in `pcall` so a single protected frame failure can't break the loop; `storedAnchors[name]` is only updated on success (a frame that fails mid-combat keeps its last-known-good anchors), and its name is tracked in `failedApplies` until a retry succeeds. If both the apply and the backup-restore `pcall` fail, `Apply` prints a one-line `[CWF]` warning instead of leaving the corruption silent. `/cwf ratio` and `/cwf toggle` also respect combat lockdown: they save the db change immediately but defer the actual `UpdateCenterFrameGeometry()` call (and the panel-manager poke it triggers) to the next `PLAYER_REGEN_ENABLED` via `CWF._pendingGeometryUpdate`.

**Taint: never call `frame:SetPoint()` / `frame:ClearAllPoints()` on Blizzard frames directly.** Use `CWF.SetPoint(frame, ...)` / `CWF.ClearAllPoints(frame)` (defined in `Core.lua`), which call the native widget methods. Edit Mode system frames (unit frames, action bars, BuffFrame, ...) replace those methods with Lua overrides that write `EditModeManagerFrame.editModeSystemAnchorDirty` and snap bookkeeping. If addon code triggers those writes, Edit Mode is tainted: you get `ADDON_ACTION_FORBIDDEN` on `TargetUnit()` when entering Edit Mode, and "attempt to compare a secret number value" errors in `CompactUnitFrame`. Reading via `GetPoint` is fine.

**Event lifecycle.** `ADDON_LOADED` does *only* `InitDB()` (SavedVariables are valid here, but UI work is not yet safe). `PLAYER_LOGIN` is the first event where touching UI (e.g. building debug-border textures) is safe. The split matters — moving UI work into ADDON_LOADED will break.

**The UI Panel subsystem (`UIPanels.lua`) is separate from the FRAME_LIST capture-and-apply.** Frames managed by Blizzard's `Blizzard_UIParentPanelManager` — `CharacterFrame`, `SpellBookFrame`, `BankFrame`, `MerchantFrame`, `MailFrame`, `PlayerTalentFrame`, `WorldMapFrame`, `AchievementFrame`, etc. — are not statically anchored. They are repositioned on every show/hide/move by a forbidden `FramePositionDelegate` frame, which assigns each open `area = "left" | "right"` panel a slot: the outermost panel on a side anchors straight to UIParent's edge, and each subsequent panel on that side anchors relative to the *actual current edge* of the panel ahead of it (a cascade). Adding these to `FRAME_LIST` doesn't work: the panel manager re-runs on every panel state change and overwrites our anchors. Instead, `UIPanels.lua` hooks the public global wrappers (`ShowUIPanel`, `HideUIPanel`, `UpdateUIPanelPositions`) via `hooksecurefunc` and, after Blizzard's pass, shifts panels inward by `(UIParent.width - CenterFrame.width) / 2` *overlap-aware*, processing each side outermost-first (edges compared in screen space): the outermost panel always gets the shift; each panel behind it is shifted only if it would now overlap the post-shift panel ahead of it — i.e. Blizzard cascaded it off pre-shift geometry that pass. Panels already cascaded off shifted geometry are left alone, so the inset is never double-counted regardless of whether the delegate's pass read canonical or live positions. This also means `WorldMapFrame`/`AchievementFrame` (registered as area "left" in some Midnight builds) are treated like any other left panel rather than force-centered: force-centering one while it still occupied a left slot desynced Blizzard's slot accounting and scrambled every other open panel's position. Center/full/doublewide/centerOrLeft panels are intentionally not adjusted (center panels use `TOP`-anchor, no horizontal offset to fix; the others are out of scope for v1). When `CenterFrame` geometry changes, `UpdateCenterFrameGeometry()` calls `UpdateUIPanelPositions(nil)` to make Blizzard reflow open panels through our hook. A panel's area is read the way Blizzard's local `GetUIPanelAttribute` does: the frame attribute `UIPanelLayout-area` once `UIPanelLayout-defined` is set, falling back to `UIPanelWindows[name].area` (a normal global). This matters because `SetUIPanelAttribute` only updates the frame attribute. WoW Forever's `PlayerSpellsFrame` is registered `centerOrLeft` but flips its live area to `left` whenever the spellbook tab is minimized (the default on first open).

## File load order

Defined in both `.toc` files (keep them identical unless a flavor-only file is intentional, see above): `FrameList.lua → Config.lua → Core.lua → UIPanels.lua → ManagedContainers.lua`. Load-time only. `Config.lua` references `CWF.CenterFrame` (created in `Core.lua`) inside `EnsureBorderLines`, but that function only runs at PLAYER_LOGIN or later. `UIPanels.lua` and `ManagedContainers.lua` call `hooksecurefunc` on Blizzard globals at top level, which requires the owning Blizzard addons to already be loaded — true for system addons by the time user addons execute. Both guard with `type(_G[name]) == "function"` so a client that lacks one degrades instead of erroring. Likewise, optional events go through `RegisterOptionalEvent` in `Core.lua` (`RegisterEvent` hard-errors on unknown event names). If you add new top-level code that touches `CWF.CenterFrame`, it must go in `Core.lua` or be deferred to PLAYER_LOGIN.

## Adding a new managed frame

Append to the `CWF.FRAME_LIST` table in `FrameList.lua`. Unknown/missing globals are silently skipped (`if frame and frame.GetNumPoints ...`), so it's safe to list frames that may not exist in every game state or client (boss frames, Forever-only swing timers / totem bar, etc.). Before adding one, check in wow-ui-source (`live` and `forever` branches) what it is actually anchored to by default. If it's parented/anchored to another frame (e.g. `MicroMenu` → `MicroMenuContainer`, managed frames → `RightManagedFrameContainer`), listing it is a no-op, and the frame to manage is the one that actually touches UIParent.

**Intentionally unmanaged (owner decision):** the micro menu and bag bar (`MicroButtonAndBagsBar`, `MicroMenuContainer`, `BagsBar`) and the raid frames (`CompactRaidFrameContainer`, `CompactRaidFrameManager`). Players place these with Edit Mode, so don't add them back. The known bank/bag overlap limitation (see ManagedContainers above) is also accepted as-is.

## SavedVariables

`CenterWoWFramesDB` (declared in the .toc). Defaults live in `CWF.DB_DEFAULTS` in `Config.lua`; `InitDB()` shallow-merges defaults into the saved table so adding a new default key is non-destructive for existing users.
